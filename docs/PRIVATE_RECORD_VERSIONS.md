# Private record versions — prepared storage and encrypted preservation

Updated November 20, 2026. R03/R12 remain Partial. This is an additive, **uninstalled** SQL candidate and a locally verified encrypted-backup extension. It does not enable history in the owner launcher, expose a browser history interface, implement Undo, or certify a release.

## Existing implementation reused

`cc_records.version` already protects optimistic writes but does not retain old contents. Existing reviewed record writers, source permissions, recently-deleted controls and AES-256-GCM workspace archives remain authoritative. `supabase/drafts/private_record_versions.sql` adds a separate prior-row ledger; it does not replace records or infer earlier versions from a counter.

For owned private tasks, notes, events, projects and School fixtures, a source BEFORE UPDATE/DELETE trigger captures the complete old row in the **same transaction**. Failed source writes roll back their capture. Unknown payload fields, original IDs, source revision and six-digit UTC metadata survive. Existing records are not rewritten or backfilled. Capture begins only after explicitly authorized installation; no earlier history is fabricated. Household rows and relationship rows are excluded from this bounded candidate and remain required release work.

The source trigger needs a narrowly scoped SECURITY DEFINER insert into the ledger. Its empty search path, exact reviewed body, trusted ownership, revoked direct execution and enabled trigger binding are checked. Clients have SELECT only, with active-session, owner and current-private-source RLS; they cannot insert, rewrite or delete ledger rows. A second trigger rejects mutation even through an accidentally privileged direct write. Readiness also pins reader/export bodies, grants, policy expression/role and RLS. Policy hashing uses the same fixed search path at installation and runtime to avoid equivalent deparse differences falsely reporting drift.

## Read and archive contracts

`list_private_record_versions` returns at most50 sparse entries and a bounded count; it omits historical bodies. Selected full snapshots require both the original source and version identity under the same source-dependent RLS. These are authenticated database RPCs, **not a browser transport**: raw UUIDs and snapshots must remain server-side when the selected-source UI is integrated.

`export_private_record_versions` provides ordered100-row cursor pages under authenticated RLS. The existing default-off private backup tool discovers the prepared readiness RPC. Only an exact PostgREST missing-function404 establishes absent storage; disconnection, denied access, malformed replies or installed-but-unprotected storage stop export. It reads source records and history twice and requires matching complete inventories before loading the key or writing a file. Pagination, per-record limits and the existing5MiB plaintext archive cap remain enforced; exceeding a cap fails rather than truncates.

The existing encrypted archive can now contain optional `recordVersions`. Archives without this property remain supported. Every entry must have an exact same-owner private source, supported kind, unique history identity, valid capture metadata and a complete private snapshot whose source ID/type/revision match. All source and historical payloads remain inside authenticated encryption; file writes retain existing private permissions, no-overwrite and reread protections. CLI summaries include counts only. The backup tool has not been run against an owner account in this milestone.

**Conflicting, unverified and unsupported-dependency history remains blocked. Eligible missing active-source history can now be imported under a separate recovery scope.** In verification-only mode (`allowRecordHistoryVerification` without import), recovery may proceed only if every archived history entry already exists exactly in the authenticated destination. It proves complete bounded source/history inventories twice before review, binds their fingerprints and repeats the proof under source/ledger transaction locks. Recovery inserts only eligible missing ordinary records; it never inserts, rewrites or deletes history. Missing, conflicting or unverified history is counted separately and blocks approval. All existing source records and history are verified after insertion; unexpected history side effects or newly exposed orphan history roll back the entire transaction. The active-source import adapter is now verified locally as described below; missing deleted-source/orphan dependencies, broader lifecycle recovery and actual platform acceptance still prevent owner activation. This is implementation work, not an owner decision.

## Activation and recovery protections

No hosted installation, production schema change or owner activation is authorized by this document. Before preparing an activation request, complete the atomic history-restore path, source-bound selected browser reader, safe reviewed Undo, account erasure/retention lifecycle and actual concurrent PostgreSQL acceptance. RLS currently hides history if its source is physically absent or no longer private; orphan-history export/lifecycle protections must be settled in implementation before enabling deletion or ownership transitions. Do not enable capture and then claim a complete backup for hidden orphan rows.

The inverse in `private_record_versions_rollback.sql` takes source/ledger locks and refuses if **any** retained history exists. Empty-ledger rollback removes only candidate objects and leaves source records exact. Never delete history to force this inverse to succeed. If installation testing fails after captures exist, keep the protected ledger and recording objects intact, disable application history entry through its future default-off scope, and prepare a separately reviewed preservation/recovery procedure. A prepared inverse is not permission to run it against an owner's database.

## Already-retained history recovery — November 20

The explicit `allowRecordHistoryVerification` repository scope now permits the safe already-retained case. Complete current source/history inventories must match twice before review; every archived history UUID and its complete original metadata/payload must match exactly. Six-digit timestamps compare by exact instant rather than milliseconds alone. Missing, conflicting and unverified entries have separate counts and block approval. Full current history is fingerprinted, so a new unrelated history entry after review also invalidates approval. Existing and current-only source/history records remain intact.

An authenticated reader cannot directly take the required ledger SHARE lock without additional table privileges. Those privileges were **not granted**. The prepared schema instead adds a narrow, pinned SECURITY DEFINER lock helper: it returns false unless the caller is authenticated with an active owner session and its current transaction already holds the exact source-table recovery lock. It only takes the ledger lock; it never reads/returns bodies or writes history. Standalone RPC calls cannot acquire that source lock first. Both source and ledger remain locked across eligibility, authorization, insertion, reread and commit. The helper is removed by the existing guarded empty inverse and covered by readiness hashes/ownership/grants.

The executor still uses one-use explicit recovery approval and existing ordinary-record insertion. After insertion it verifies the entire expected source inventory and unchanged complete history. Unexpected trigger-created history or previously hidden orphan history becoming visible forces transaction rollback. A lost acknowledgement is not retried. Existing archived history is retained, not re-created or presented as imported original capture facts.
