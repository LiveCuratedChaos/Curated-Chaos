# Routine manual autosave coordinator — isolated foundation

`src/manual-autosave-session.mjs` coordinates existing first-party manual record updates through an injected authenticated workspace client. It is not mounted in the manual editor, reviewed workspace, production runtime or static asset allowlist. The owner's app is unchanged. `tests/fixtures/manual-autosave-workbench.html` is a disposable test UI served only by Playwright interception; it is not a new public route.

## Behavior and reuse

- Only verified active owner-private `CC_MANUAL_WORKSPACE` records are accepted. Task project scope is checked with the existing manual normalizer. The coordinator reuses the existing project/task change validators; current payload extensions, status, recurrence fields, progress options and checklist contents are preserved.
- Initial eligible fields are project title/summary and task title/description/date/priority. Creation, completion/status, checklist changes, project memberships, recurrence, AI/provider commands and approval flags are excluded. Those workflows and their approval requirements remain intact; this is sequencing, not removal from agreed scope.
- Routine edits debounce (600 milliseconds by default), skip unchanged payloads and coalesce rapid typing. Exactly one write is in flight. Newer typing is retained and subsequently saved against the confirmed next version. Invalid input cancels pending saves rather than sending an older valid draft.
- Each operation uses a unique UUID. An acknowledgement must match its operation, record, owner/provenance, section, full intended payload and exact next version. Existing server-side version guards, idempotent receipts and atomic history remain authoritative.
- Confirmed saves expose one guarded Undo of the latest autosave batch. Undo reuses the server's target-operation check and must acknowledge the previous payload at the exact next version. It is unavailable while edits are pending/invalid, a write is active, the result is uncertain or the session is closed. Only the immediately previous acknowledged record is held in page memory to verify Undo; no durable cache or full payload history is created.
- Any rejected/lost/mismatched/replayed acknowledgement freezes subsequent writes and automatic retries. Later typing remains available in memory for an eventual recovery UI; no refresh-and-overwrite or automatic rebase occurs. A server error cannot be used as proof that no write committed. Server error text is not exposed.
- `clear()` cancels queued timers, blocks not-yet-dispatched writes, clears public snapshots/drafts/Undo state and ignores late responses. A request already dispatched cannot be unsent; the authenticated server still enforces its access/version rules. UI integration must wire clear to account/session changes and the established lifecycle policy.

Canonical JSON comparison moved to the browser-safe `src/stable-json.mjs`; the existing server path re-exports it so repository/service imports and JSONB comparison behavior are preserved.

## Acceptance and limits

Seventeen targeted unit and isolated SQL/HTTP tests pass. They cover coalescing, no-op edits, serialized versions, invalid typing, loss of an acknowledgement after the SQL commit, competing-writer/Undo conflicts, forged/stale/replayed receipts, protected commands, cancellation before dispatch, late-response clearing, timer/operation-identity reuse, extension/text preservation and session closure. SQL-backed tests use the existing ephemeral PGlite fixture and existing draft schema; they do not contact Supabase or apply any migration. Fixtures close after each case.

Six Playwright cases pass: three journeys each at desktop and narrow Chromium sizes. The actual coordinator and cookie/CSRF client communicate with disposable SQL-backed records. Journeys cover autosave/history/Undo, newer typing during a delayed save, and a committed save with a lost response that retains copyable edits, makes no retry and clears when closed. The initial fixture test run found an ambiguous test status selector (HTML output has an implicit status role); the test workbench markup was corrected and all six cases passed. No product code was changed to bypass that check.

This does not complete CC-HIST-01 or CC-OFF-01. Current editor integration, full routine fields/checklist/membership semantics, grouping/Undo UX, previous-version viewing, reviewed-engine payload/provenance convergence, migration acceptance, encrypted offline queue/conflicts and physical Safari/iPhone acceptance remain open. A temporarily offline request enters uncertain state; memory-only draft retention is not durable offline support. No live service, provider scope, saved real record, database schema, migration, Apple Calendar refresh or running app is changed. Final integrated regression: all 2,078 Mac offline tests passed, zero failures/cancellations/skips or platform exclusions; privacy/content scan, whitespace and launcher checks passed. The complete desktop/narrow Chromium suite passed all 110 cases in one run. These are fictional/browser-engine results, not physical Safari/iPhone, hosted deployment or real-data acceptance.
