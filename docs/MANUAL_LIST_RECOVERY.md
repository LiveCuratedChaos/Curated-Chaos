# Manual verified-list recovery preparation

Local follow-up after approved PR15 merge and draft PR16 publication. The candidate and original/integration checkouts remain unchanged; Apple Calendar refresh stays off.

The manual controller previously assigned a refresh result before validating it. A malformed, foreign, mixed-provenance, duplicate or oversized response could hide the checked view and the newer editor behind a rendering error. It now checks the entire array with the established owner/private/manual model and exact project/task coverage before assigning rows. Replayed mutation receipts use the same list verification; an invalid refreshed list cannot establish a confirmed save or resurrect an old receipt.

Failed reads retain the prior checked view and unsent draft, while clearly stating that a verified fresh list was unavailable and the old view may be out of date. An uncertain save remains locked after refresh failure and explicitly states that no changes were retried. Successful later reads recover normally. Initial invalid responses never enter live view state. Session clearing still retires pending work and clears private state; no stale-view retention overrides sign-out/revocation handling.

These client checks supplement, never replace, server actor/session/RLS/version enforcement and coherent repository reads. No authorization is inferred from a rendered list, and no new read/write route, schema, provider access, conversion or retry is introduced. The per-refresh model check adds one bounded normalization pass; the80-project regression still prevents per-card amplification.
