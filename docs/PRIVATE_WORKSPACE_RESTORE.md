# Private workspace archive restoration

Updated November20, 2026. The original November17 foundation is extended below and by `PRIVATE_RECORD_VERSIONS.md`. This remains a bounded server foundation, not an enabled owner recovery flow or full disaster-recovery acceptance. `docs/RELEASE_CHECKLIST.md` remains authoritative for release status.

## Existing protections retained

Encrypted archive authentication still binds its project, owner, key and snapshot identity. The existing comparison CLI remains comparison-only: it has no restore flag. No real archive, key, credentials or hosted database was accessed to build or test this path.

`server/private-workspace-restore-executor.mjs` reuses that archive inspection and comparison. `private-workspace-restore-contract.mjs` restricts insertion to supported ordinary private notes, manual tasks without recurrence/approval dependencies, private projects, canonical School program/course records and private manual Calendar events. Existing validators remain authoritative. Supported event/project/School extensions remain exact; unsupported types/origins/dependencies are refused rather than guessed. Separate false-by-default graph/history scopes govern additional recovery paths.

An archive containing a missing active relationship cannot receive an executable review. Inserting either kind of active relationship currently invokes existing triggers that advance its task/project revisions and update times. Those triggers stay enabled. Missing retired relationship rows and other archived tombstones are retained in the archive and reported separately; they are never recreated as active records. Unknown, recurring, approval-linked, settings, provider and other missing types remain unsupported by this bounded executor. Full relationship/history recovery is still a release gate.

## Review and transaction

Preparation reads two complete bounded private inventories, validates their full metadata and requires matching fingerprints. It returns counts and one opaque review handle, no contents, raw record IDs or insertion payloads. Reviews expire after at most five minutes and are bound to an active owner/session. Queued preparations, reviews and active saves are bounded. Cancellation/revocation/disposal invalidates work and owned key/archive buffers are cleared when no longer needed.

Execution consumes its review once and requires a separately supplied server authorization callback, which defaults to refusal. The repository target must match the archive target. Changed current rows, additions, removals, versions, deletion states or even microsecond timestamp changes invalidate approval. A changed session also stops execution. Current-only and newer existing records remain exact; no upsert, replacement or deletion is available.

`server/private-workspace-restore-repository.mjs` requires a trusted factory supplying one exclusive **idle** SQL connection already bound to the authenticated actor's existing JWT claims, plus a separate destination verifier that defaults to refusal. The verifier must establish the connection's actual approved database identity; matching caller-supplied strings is insufficient. Never supply a service/administrator connection, a pooled connection with an existing transaction, or a browser-defined adapter. Both SQL role and active owner/session are checked inside the database.

The adapter starts READ COMMITTED, sets3s lock and20s statement/idle-transaction timeouts, and takes SHARE ROW EXCLUSIVE on `cc_records` with NOWAIT. This conflicts with ordinary record writes as well as other restores; an owner advisory lock would not provide that guarantee. Recovery is a rare bounded operation; it refuses a busy table instead of waiting for ordinary work. A dedicated fresh connection factory is still required before any real activation; no connection factory or HTTP/CLI is wired here.

Within that transaction, the full inventory is checked again. Only missing supported active records are inserted. Exact acknowledgements and a complete reread must match the expected union of every pre-existing row and the reviewed insertions. Timestamp comparisons normalize equivalent timezone representations while preserving all six PostgreSQL fractional digits. Version, payload, origin, deletion state and creation/update instants are preserved. Verification/session failures throw before COMMIT and roll back all changes, including trigger side effects.

After an attempted insertion, any lost response or commit acknowledgement is reported as uncertain. Revocation/disposal while COMMIT is already in flight can likewise only yield uncertainty, not a guaranteed rollback. The executor never retries it and never claims the transaction rolled back without evidence. Inspect current copies and prepare a new review; an already committed exact insertion becomes unchanged instead of a duplicate. Authorization inside the transaction must be a fast noninteractive server check, never a user prompt or external permission flow.

## Acceptance and recovery limits

Fictional embedded PostgreSQL tests exercise encrypted preparation through actual SQL insertion/commit, exact original metadata, existing/foreign record preservation, expired or wrong sessions, table lock lifetime and rollback after induced side effects. In-memory transaction tests cover lost commit acknowledgement, duplicate approvals, revocation during preparation/save, staleness, unsupported dependencies and precision differences. No app restart or hosted migration is needed for these modules.

Before real activation: integrate a fresh authenticated connection factory, verify its target/schema and managed-service compatibility, prove real concurrent-writer refusal/timeouts and connection cleanup, finish supported relationship/history restoration, expose the established review/approval workflow, and rehearse recovery against disposable fictional archives in an approved isolated destination. Full hosted Auth/storage restore and measured disaster recovery remain separate gates in DATABASE_RECOVERY_ACCEPTANCE.md.

The original November17 foundation needed no database migration. Current rollback keeps all new recovery scopes false and the owner launcher unchanged; these modules are now shared and must not simply be removed. Generic history has an additive prepared SQL package with an empty-ledger-only inverse; follow `PRIVATE_RECORD_VERSIONS.md` and never delete retained history to force schema rollback. A confirmed real restore would require a separate reviewed recovery: preserve the original encrypted archive, inspect exact restored identities and subsequent edits/links, and use guarded existing removal workflows where appropriate. Never bulk-delete records or overwrite later edits to reverse a restore. A lost acknowledgement requires inspection before any further action.

## Eligible tombstone reconstruction — November20

Both executor and repository require separate explicit `allowArchivedDeletedRestore`, false by default. A supported owned-private record removed within the existing90-day window may be inserted as the **same deleted row**, preserving its original removal date, ID, revision, timestamps, payload and associations. It is not made active and gets no new recovery period. Review reports deleted-row counts; its lease ends at the earliest original retention deadline. Unsupported/recent deleted records block approval; expired data is not recreated. Missing historical dependencies continue to block rather than disappear.

School tombstones additionally require the new pinned readiness capability. The prepared School guard permits a deleted INSERT only for its active authenticated owner, original removal within90days and an already-held source-table recovery lock. Its temporary validation copies never change the actual row or parent. Deleted courses may retain their deleted owned program; active courses still require an active program. Ordinary creation without that recovery context remains refused. Readiness generators and dependent canonical-task artifacts are regenerated from the exact reviewed bodies, retaining all checks.

The combined-schema two-database drill reconstructs task/note/event/project/program/course tombstones plus exact history, proves zero active restored rows and validates ordinary Recently Deleted using the original removal date. At the original90-day deadline those entries expire instead of receiving a fresh window. Missing scope/School protection, incompatible active-parent associations, expiry during approval and lost history acknowledgement roll back or refuse the entire operation. Existing destination records remain exact. This does not implement actual retention deletion or account erasure.
