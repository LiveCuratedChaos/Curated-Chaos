# Curated Chaos delivery coordination

## Scope and authority

Preserve every agreed feature in `docs/APPROVED_BLUEPRINT.md`, including retained later-release commitments. Sequencing is not scope reduction. Use `docs/PRODUCT_SCOPE_LEDGER.md` as the current capability/evidence map and `docs/AI_DELIVERY_PLAN.md` as the delivery order. Keep `docs/COMPLETION_PLAN.md` as historical evidence; do not infer present status from old pending entries or test counts.

Local implementation, synthetic tests and reversible development work are authorized. Preserve explicit approvals for live deployment, production migration, actual database changes, new provider/data scopes, household invitations, paid services and owner-only account/OS actions. Prepare a concrete bounded acceptance package before asking. Bundle related development fixture tests and preview promotion into one understandable request; do not ask separately for each field/button. Never interpret an approval as unlimited unrelated real-data access.

## One integration lead

The lead owns shared contracts, auth/session boundaries, routing, schema integration, source baseline, merge order and final validation. Parallel agents use separate branches/worktrees and disjoint file ownership. Use up to three workers plus the lead when the session supports four slots. Do not override model choices or assume unattended background execution. Review worker changes before integration; the author is not the only reviewer.

Shared auth/router/schema/controller/style edits go through the lead. Domain, integration and household/document workers consume published interfaces rather than independently redesigning them. Prefer whole accepted workflows over duplicate preview handlers and one-control delivery loops.

## Preserve the working product

Do not restart or alter the owner's running preview without readiness approval. Use isolated staging, separate cookies and ephemeral test sockets. Do not inspect real note bodies, financial details or credentials for routine development. Never print secrets or private record contents. Do not copy `.env*` (except sanitized `.env.example`), `.local`, private keys, recovery archives or provider storage into branches/artifacts.

The original checkout contains accepted uncommitted work and may continue changing. The local integration baseline was captured without changing its HEAD/index. Do not reset, stage, commit, cherry-pick or overwrite that checkout as part of this branch's integration. Capture/reconcile later parent work explicitly. Do not publish branches, deploy or migrate merely because local checks pass.

## Reuse and acceptance

Reuse domain models, provider adapters, safe mutations, RLS/session enforcement, encrypted archives and accepted tests. Do not remove fictional-data guards to manufacture production support; introduce explicit production record/provenance contracts and migration tests.

Production routine user edits need the agreed autosave/Undo/history path; AI/provider/sensitive actions retain their approval requirements. Temporary draft clearing is not completed offline support. Implement protected offline queues/conflicts/cache policies separately; never weaken current protections silently.

A batch is complete only with implementation, meaningful automated tests, integrated browser journeys where relevant, privacy checks, failure/cleanup evidence, scope-ledger updates and explicit limitations. A passing local suite is not evidence of production hosting, physical-device support, ongoing provider sync, guardian safety or full disaster recovery. Keep those release gates separate.
